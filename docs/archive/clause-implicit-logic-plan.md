## 一、问题定义

### 1.1 什么是"条款隐含逻辑"

条款隐含逻辑是指法规条文中存在的、无法仅从单一条文文本直接理解的语义关联和上下文依赖。当审核系统仅检索到某一条文而未感知其关联条文时，可能导致：

- **误判合规**: 漏掉了例外条款，将本应豁免的内容判定为违规
- **误判违规**: 未注意到某禁止性条款已被另一条款限定适用范围
- **引用不完整**: 只引用主条款而未引用补充条件或定义条款
- **逻辑不自洽**: 审核推理与法规体系存在矛盾

### 1.2 真实案例（来自三部监管法规）

#### 案例1: 禁止+例外 — 《保险销售行为管理办法》第十九条 vs 第十四条

- **条款A（第十九条）**: 保险公司决定停止销售某一保险产品或者调整某一保险产品价格的，应当在官方线上平台显著位置和营业场所公告
- **条款B（第十九条但书）**: 但保险公司在经审批或者备案的费率浮动区间或者费率参数调整区间内调整价格的**除外**
- **隐含逻辑**: 如果只看到"调整价格应当公告"，而未看到"费率浮动区间内调整除外"，则费率浮动区间内的正常调价也会被误判为违规
- **关系类型**: 例外条款（例外）

#### 案例2: 术语定义+使用 — 《金融产品网络营销管理办法》第三条 vs 第九条

- **条款A（第三条）**: 本办法所称金融产品，是指金融机构设计、开发、销售的产品和服务，包括但不限于存款、贷款、资产管理产品、**保险**、支付、贵金属等
- **条款B（第九条第四项）**: 夸大保险责任或保险产品收益，将保险产品收益与存款、资产管理产品等金融产品简单类比
- **隐含逻辑**: 第九条禁止"将保险产品与存款、资产管理产品简单类比"，而第三条明确定义了"金融产品"包含保险、存款、资产管理产品。审核时如果只检索到第九条而不知道第三条的定义，就无法准确理解"简单类比"的边界——第三条本身将保险与存款并列，但第九条禁止的是"简单类比"而非"并列提及"
- **关系类型**: 定义条款（定义依赖）

#### 案例3: 引用+补充 — 《保险销售行为管理办法》第四十三条 vs 第三条

- **条款A（第四十三条）**: 违反本办法**第三条**、第三十九条规定的，由金融监管总局及其派出机构依照《中华人民共和国保险法》等法律法规和监管制度的相关规定处理
- **条款B（第三条）**: 保险公司、保险中介机构及其保险销售人员不得欺骗投保人、被保险人、受益人或者保险合同利害关系人……
- **隐含逻辑**: 第四十三条是第三条的法律后果条款。如果审核发现营销内容涉嫌欺骗，应同时引用第三条（禁止性规定）和第四十三条（法律后果），增强审核结论的权威性
- **关系类型**: 处罚引用（法律后果）

#### 案例4: 跨文档引用 — 《金融产品网络营销管理办法》第三十三条 vs 第九条、第十六条

- **条款A（第三十三条）**: 第三方互联网平台违反本办法**第八条、第九条、第十六条第一款、第二十三条、第二十四条**规定开展金融产品网络营销的，市场监管部门可依据《中华人民共和国广告法》《中华人民共和国反不正当竞争法》予以处置
- **条款B（第九条）**: 网络营销宣传不得含有以下内容……
- **条款C（第十六条）**: 不得利用学术机构、行业协会、专业人士的名义或者形象作推荐、证明
- **隐含逻辑**: 第三十三条将多条禁止性条款与具体的法律后果和执法部门关联起来。审核时如果只引用第九条判定违规，但未提及第三十三条，则无法说明违规的法律后果和执法依据
- **关系类型**: 处罚引用 + 明确引用（法律后果 + 引用）

#### 案例5: 前提条件 — 《互联网保险业务监管办法》第五十六条 vs 第五十一条、第五十三条

- **条款A（第五十六条）**: 保险中介机构应对互联网保险业务实行统一、垂直管理，具体要求**参照本办法第五十一条、第五十三条规定**
- **条款B（第五十一条）**: 保险公司总公司应对互联网保险业务实行统一、垂直管理……
- **条款C（第五十三条）**: 保险公司分支机构可在上级机构授权范围内为互联网保险业务提供查勘理赔……
- **隐含逻辑**: 第五十六条对保险中介机构的要求直接引用了第五十一条和第五十三条对保险公司的要求。审核中介机构合规性时，必须同时查看第五十一条和第五十三条的完整内容，才能理解"统一、垂直管理"的具体含义
- **关系类型**: 前提条件 + 明确引用（前提条件 + 引用）

#### 案例6: "除…外"例外 — 《保险销售行为管理办法》第二十五条 vs 第二十五条但书

- **条款A（第二十五条正文）**: 保险公司或者受其委托及与其合作的保险中介机构、保险销售人员应当在投保人投保前以适当方式向投保人提供格式条款及该保险产品说明，并就以下内容向投保人作出明确提示……
- **条款B（第二十五条但书）**: 保险公司、保险中介机构在销售保险产品时，经投保人同意，对于权利义务简单且投保人在三个月内再次投保同一保险公司的同一保险产品的，**可以合理简化相应的提示内容**
- **隐含逻辑**: 如果只看到正文要求"明确提示"全部内容，而未看到但书的简化例外，则对续保场景的审核会产生误判
- **关系类型**: 例外条款（例外）

#### 案例7: 跨文档概念依赖 — 《保险销售行为管理办法》第四十七条 vs 《互联网保险业务监管办法》

- **条款A（第四十七条）**: 保险公司、保险中介机构开展保险销售行为，除遵守本办法相关规定外，应当符合法律法规和金融监管总局关于财产保险、人身保险、**保险中介销售管理的其他相关规定**
- **条款B（《互联网保险业务监管办法》全文）**: 对互联网保险销售行为的具体规定
- **隐含逻辑**: 第四十七条明确指向了"其他相关规定"，而《互联网保险业务监管办法》正是这些"其他相关规定"之一。当审核互联网保险销售行为时，仅引用《保险销售行为管理办法》是不够的，必须同时考虑《互联网保险业务监管办法》的相关条款
- **关系类型**: 补充具体化 + cross_document（补充 + 跨文档）

## 二、关系类型分类

### 2.1 关系类型定义

| 关系类型 | 英文标识 | 含义 | 方向性 | 典型模式 |
|---------|---------|------|--------|---------|
| 引用 | `明确引用` | A引用B的条文内容 | A→B（A引用B） | "依照第X条"、"适用第X条"、"参照第X条" |
| 例外 | `例外条款` | B是A的例外/豁免 | B→A（B豁免A） | "除…外"、"但…除外"、"另有规定的除外" |
| 补充 | `补充具体化` | B补充A的条件或要求 | B→A（B补充A） | "还应当…"、"同时…"、"并…" |
| 定义 | `定义条款` | A定义术语，B使用该术语 | A→B（A定义，B使用） | "本办法所称XX是指…" |
| 冲突 | `冲突` | A和B存在潜在冲突 | 无方向（双向） | 同一事项不同规定 |
| 前提 | `前提条件` | A是B的前提条件 | A→B（A是B的前提） | "在满足…条件下"、"经…批准后" |
| 后果 | `处罚引用` | B是A的法律后果 | A→B（A的后果是B） | "违反第X条的，…"、"…由…依照…处理" |
| 修订 | `amendment` | B修订/替代A | B→A（B修订A） | "第X条修订为…"、"自X日起，第X条修改为" |
| 适用 | `适用范围` | B限定A的适用范围 | B→A（B限定A） | "…适用本办法"、"…不适用本办法" |

### 2.2 关系类型的审核影响

| 关系类型 | 对审核结论的影响 | 处理优先级 |
|---------|----------------|-----------|
| `例外条款` | 可能翻转合规判定（违规→合规） | **P0 — 必须处理** |
| `前提条件` | 可能影响违规判定（条件不满足则不违规） | **P0 — 必须处理** |
| `定义条款` | 影响术语理解准确性 | P1 |
| `明确引用` | 影响引用完整性 | P1 |
| `处罚引用` | 增强审核结论权威性 | P2 |
| `补充具体化` | 补充审核依据 | P2 |
| `适用范围` | 确定法规适用范围 | P1 |
| `冲突` | 需人工裁决 | P2 |
| `amendment` | 确定法规时效性 | P1 |

### 2.3 关系类型的组合场景

同一对条款之间可能存在多种关系，需支持多关系并存：

| 场景 | 关系组合 | 示例 |
|------|---------|------|
| 引用+例外 | A引用B，且B是A的例外 | 第四十三条引用第三条，且第三条是第四十三条的触发条件 |
| 定义+补充 | A定义术语，B补充该术语的使用规则 | 第三条定义"金融产品"，第九条补充金融产品宣传的禁止内容 |
| 前提+后果 | A是B的前提，B是A的后果 | 第三条是禁止性规定，第四十三条是违反第三条的后果 |

CREATE TABLE IF NOT EXISTS clause_relations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    from_doc TEXT NOT NULL,
    from_article TEXT NOT NULL,
    to_doc TEXT NOT NULL,
    to_article TEXT NOT NULL,
    relation_type TEXT NOT NULL,
    confidence REAL NOT NULL DEFAULT 1.0,

    is_verified INTEGER NOT NULL DEFAULT 0,
    verified_by INTEGER,
    verified_at TEXT,
    notes TEXT NOT NULL DEFAULT '',

CREATE INDEX IF NOT EXISTS idx_clause_relations_from
    ON clause_relations(from_doc, from_article);
CREATE INDEX IF NOT EXISTS idx_clause_relations_to
    ON clause_relations(to_doc, to_article);

### 3.3 传递关系处理

#### 3.3.1 传递闭包计算

当存在 A→B→C 的引用链时，A与C之间存在**隐含传递关系**。系统需计算传递闭包：

```
A 明确引用 B, B 明确引用 C
→ A 隐含引用 C (传递深度=2)
```

**实现方式**:

1. **实时计算**: 每次查询时从数据库递归遍历关系图，计算传递闭包
2. **预计算+缓存**: 启动时预计算传递闭包，结果缓存到内存字典中
3. **Demo选择**: 预计算+缓存（条款数量有限，约109条，关系数量预计<200，计算开销极小）

**传递关系标记**: 传递关系不写入数据库，仅在内存中计算和缓存，标记 `is_transitive=True` 和 `depth=N`。

#### 3.3.2 传递深度限制

| 场景 | 最大深度 | 说明 |
|------|---------|------|
| Demo阶段 | 2 | 1级直接关系 + 2级传递关系 |
| 生产阶段 | 3 | 支持更深层的法规推理 |

### 3.4 循环引用处理

#### 3.4.1 检测算法

使用深度优先搜索（DFS）检测有向图中的环：

```python
def detect_cycles(relations):
    graph = build_adjacency_list(relations)
    visited = set()
    rec_stack = set()
    cycles = []

    def dfs(node, path):
        visited.add(node)
        rec_stack.add(node)
        for neighbor in graph.get(node, []):
            if neighbor not in visited:
                dfs(neighbor, path + [neighbor])
            elif neighbor in rec_stack:
                cycle_start = path.index(neighbor)
                cycles.append(path[cycle_start:] + [neighbor])
        rec_stack.remove(node)

    for node in graph:
        if node not in visited:
            dfs(node, [node])
    return cycles
```

#### 3.4.2 循环引用处理策略

| 循环类型 | 示例 | 处理策略 |
|---------|------|---------|
| 自引用 | A→A | 标记为 `self_reference`，忽略该关系 |
| 双向引用 | A→B, B→A | 保留两条关系，但传递闭包计算时设置 `visited` 集合防止无限循环 |
| 长环 | A→B→C→A | 保留所有关系，传递闭包计算时检测环并截断 |

**核心原则**: 传递闭包遍历时维护 `visited` 集合，已访问节点不再入队，天然防止无限循环。

#### 4.1.1 正则模式定义

#### 4.1.2 正则提取实现要点

```python
import re

REFERENCE_PATTERNS = [
    (r'依照第([一二三四五六七八九十百]+)条', '明确引用'),
    (r'适用第([一二三四五六七八九十百]+)条', '明确引用'),
    (r'参照第([一二三四五六七八九十百]+)条', '明确引用'),
    (r'按照第([一二三四五六七八九十百]+)条', '明确引用'),
    (r'违反[^。]*第([一二三四五六七八九十百]+)条', '处罚引用'),
]

EXCEPTION_PATTERNS = [
    (r'除[^。]{0,50}外[,，]', '例外条款'),
    (r'但[^。]{0,80}除外', '例外条款'),

#### 4.2.3 RAG搜索发现关系（推荐新增方法）

**核心思路**：对每个条款，构造一个查询语句送入RAG引擎检索语义相关条款，再由LLM判断检索结果中是否存在真实的逻辑关系。

**为什么这个方法可行**：

1. **复用现有基础设施**：RAG引擎和向量数据库已经就绪，不需要额外的工具或服务
2. **语义相似性是逻辑关系的前置条件**：有逻辑关系的条款通常在语义上也相关（如"禁止欺骗"和"违反禁止欺骗的后果"），RAG能高效召回这些候选
3. **两步过滤保证精确性**：RAG负责"召回"（高召回率），LLM负责"判别"（高精确率），类似审核流水线本身的RAG→LLM架构
4. **天然支持跨文档发现**：向量检索不区分文档来源，同一查询可以同时召回不同文档的相关条款

**实际验证结果**（2026-05-17，关键词检索模式）：

| 测试场景 | 查询条款 | 期望找到 | RAG Top5是否包含 | 分析 |
|---------|---------|---------|----------------|------|
| 引用关系 | 第四十三条 | 第三条 | ❌ 未命中 | 关键词模式下score均为0，排序不稳定；向量模式下预期可命中 |
| 引用关系 | 第五十六条 | 第五十一条、第五十三条 | ❌ 未命中 | 同上 |
| 定义依赖 | 第九条 | 第三条 | ❌ 未命中 | 定义条款与使用条款的语义距离较远，关键词模式难以关联 |
| 跨文档 | 第四十七条 | 互联网保险业务监管办法条款 | ⚠️ 部分命中 | 找到了互联网保险的条款，但不是最相关的 |

**关键发现**：
- **关键词检索模式**下效果有限，因为关键词匹配无法捕捉语义关联
- **向量检索模式**（有DashScope API Key时）预期效果显著提升，因为向量天然编码了语义相似性
- 即使RAG召回的Top5不完全精准，LLM判别步骤可以过滤掉无关结果，只保留真正有逻辑关系的条款

**查询语句构造策略**：

**查询策略对比**：

| 策略 | 查询构造 | 适用场景 | 预期召回率 |
|------|---------|---------|-----------|
| 原文+意图 | 条款原文前200字+"与其他条款的隐含关系" | 通用 | 中（依赖向量质量） |
| 核心概念 | LLM提取核心概念后检索 | 长条款、概念密集条款 | 高 |

**推荐组合策略**：对每个条款执行2次检索——
1. **原文+意图查询**：发现语义相关的条款（通用）

**完整流程**：

```

  Step 5: 入库 → 写入clause_relations表
```

### 4.3 方法3: 人工验证

#### 4.3.1 验证流程

**设计原则**：人工标注不是关系发现的主要方法，而是对正则和LLM提取结果的验证手段。人工验证的职责是：

### 5.3 关联条款扩展步骤设计

#### 5.3.1 核心算法

```python
def expand_related_clauses(reranked_articles, clause_relations, max_depth=2, max_related=10):
    """
    对重排序后的Top-K条款，扩展其关联条款。

    Args:
        reranked_articles: 重排序后的条款列表
        clause_relations: 条款关系数据（内存缓存）
        max_depth: 最大传递深度（Demo=2）
        max_related: 最大关联条款数量

    Returns:
        expanded_articles: 包含原始条款和关联条款的列表
    """
    expanded = list(reranked_articles)
    seen = {(a['doc_name'], a['article_number']) for a in expanded}
    queue = [(a, 0) for a in reranked_articles]

    while queue:
        article, depth = queue.pop(0)
        if depth >= max_depth:
            continue

        relations = lookup_relations(
            doc_name=article['doc_name'],
            article_number=article['article_number'],
            clause_relations=clause_relations,
        )

        for rel in relations:
            key = (rel['to_doc'], rel['to_article'])
            if key not in seen and len(expanded) < len(retrieved_articles) + max_related:
                related_article = fetch_article(rel['to_doc'], rel['to_article'])
                if related_article:
                    related_article['relation_type'] = rel['relation_type']
                    related_article['relation_source'] = article['article_number']
                    related_article['relation_depth'] = depth + 1
                    expanded.append(related_article)
                    seen.add(key)
                    queue.append((related_article, depth + 1))

    return expanded
```

#### 5.3.2 关系查找优先级

当检索到条款A时，按以下优先级扩展关联条款：

| 优先级 | 关系类型 | 原因 |
|--------|---------|------|
| 1 | `例外条款` | 可能翻转合规判定 |
| 2 | `前提条件` | 可能影响违规判定条件 |
| 3 | `定义条款` | 影响术语理解 |
| 4 | `明确引用` | 补充引用完整性 |
| 5 | `适用范围` | 确定适用范围 |
| 6 | `补充具体化` | 补充审核依据 |
| 7 | `处罚引用` | 增强结论权威性 |

#### 5.3.3 引用跟随深度

| 深度 | 含义 | Demo | 生产 |
|------|------|------|------|
| 0 | 不跟随引用 | ❌ | ❌ |
| 1 | A→B（只跟随直接引用） | ✅ 默认 | ✅ |
| 2 | A→B→C（跟随二级引用） | ✅ 可选 | ✅ 默认 |

### 5.4 防止无限循环

#### 5.4.1 算法保障

```python
def expand_with_loop_protection(retrieved, relations, max_depth=2, max_related=10):
    visited = set()
    results = []
    queue = deque()

    for article in retrieved:
        key = (article['doc_name'], article['article_number'])
        visited.add(key)
        queue.append((article, 0))

    while queue:
        current, depth = queue.popleft()

        if depth >= max_depth:
            continue

        for rel in get_relations(current['doc_name'], current['article_number'], relations):
            target_key = (rel['to_doc'], rel['to_article'])

            if target_key in visited:
                continue

            if len(results) >= max_related:
                return results

            visited.add(target_key)
            target_article = fetch_article(rel['to_doc'], rel['to_article'])
            if target_article:
                results.append(target_article)
                queue.append((target_article, depth + 1))

    return results
```

**三重保障**:
1. `visited` 集合：已访问节点不再入队
2. `max_depth` 限制：递归深度上限
3. `max_related` 限制：关联条款总数上限

| 深度截断 | 超过 `max_depth` 的关联不再跟随 |
| 数量截断 | 关联条款总数超过 `max_related` 时停止扩展 |
| 优先级过滤 | 优先保留 `例外条款` 和 `前提条件` 类型的关联 |
| 摘要替代 | 深度>1的关联条款只展示摘要（前100字），不展示全文 |
| LLM判断 | 让LLM判断哪些关联条款与当前审核内容相关，只保留相关的 |

### 5.6 Workflow步骤集成

在 `review_agent.py` 的 `_build_workflow` 中新增步骤：

```python
def _build_workflow(self):
    engine = WorkflowEngine()
    engine.register_step("extract", self._step_extract)
    engine.register_step("rule_check", self._step_rule_check)
    engine.register_step("rag_retrieve", self._step_rag_retrieve)
    engine.register_step("rerank", self._step_rerank)
    engine.register_step("expand_relations", self._step_expand_relations)  # 新增
    engine.register_step("llm_reason", self._step_llm_reason)
    engine.register_step("format", self._step_format)
    engine.register_step("validate", self._step_validate)
    engine.register_step("crosscheck", self._step_crosscheck)
    engine.register_step("risk_assess", self._step_risk_assess)
    return engine
```

## 七、极端情况处理

### 7.1 自引用条款

| 场景 | 示例 | 处理 |
|------|------|------|
| 条款引用自身 | 极少见，但理论上可能 | 检测到 `from_article == to_article` 时，标记为 `self_reference`，不纳入关联扩展 |

```python
if from_doc == to_doc and from_article == to_article:
    logger.warning(f"自引用检测: {from_doc} 第{from_article}条")
    relation.relation_type = "self_reference"
    # 不纳入关联扩展
```

### 7.2 循环引用

| 场景 | 示例 | 处理 |
|------|------|------|
| A→B→A | 条款A引用B，B又引用A | 传递闭包计算时 `visited` 集合防止无限循环 |
| A→B→C→A | 三角引用 | 同上 |
| A→B→C→…→A | 长环 | 同上 |

**关键**: 所有遍历算法必须维护 `visited` 集合，这是防止无限循环的根本保障。

### 7.3 超长引用链

| 场景 | 处理 |
|------|------|
| A→B→C→…→Z（26+级） | `max_depth` 硬限制截断 |
| 同一深度有大量分支 | `max_related` 总数限制截断 |
| 深度>1的关联条款Token过多 | 只展示摘要，不展示全文 |

**Demo阶段**: `max_depth=1`, `max_related=10`
**生产阶段**: `max_depth=2`, `max_related=15`

### 7.4 引用目标不存在

| 场景 | 示例 | 处理 |
|------|------|------|
| 条款编号不存在 | A引用"第九十九条"但文档只有50条 | 标记 `target_missing=True`，记录但不扩展 |
| 跨文档引用目标不在库中 | A引用另一文档的条款，但该文档未入库 | 标记 `target_doc_missing=True`，记录但不扩展 |
| 条款编号格式异常 | "第3条"（阿拉伯数字）vs "第三条"（中文数字） | 统一转换中文数字后再查找 |

```python
CN_NUM_MAP = {
    '一': 1, '二': 2, '三': 3, '四': 4, '五': 5,
    '六': 6, '七': 7, '八': 8, '九': 9, '十': 10,
    '十一': 11, '十二': 12, ...
}

def normalize_article_number(article_str):
    if article_str.isdigit():
        return cn_from_int(int(article_str))
    return article_str
```

### 7.5 矛盾关系

| 场景 | 示例 | 处理 |
|------|------|------|
| 同一对条款有冲突关系 | A→B标记为`例外条款`，又有A→B标记为`补充具体化` | 允许多关系并存，在审核时分别展示 |
| 关系方向矛盾 | A→B是`明确引用`，B→A也是`明确引用` | 正常情况（互相引用），两条都保留 |

**原则**: 不自动解决矛盾，全部保留，由LLM在推理时判断或由人工验证时裁决。

### 7.6 多关系并存

| 场景 | 处理 |
|------|------|
| A和B之间同时有`明确引用`和`例外条款` | 两条关系都保留，UNIQUE约束按 `(from_doc, from_article, to_doc, to_article, relation_type)` 组合去重 |
| A和B之间有3种以上关系 | 全部保留，前端按优先级排序展示 |

### 7.7 跨文档引用

| 场景 | 示例 | 处理 |
|------|------|------|
| 明确跨文档引用 | 《金融产品网络营销管理办法》第三十三条引用《广告法》 | `to_doc` 填写被引文档名，即使该文档不在库中也记录 |
| 隐含跨文档引用 | 《保险销售行为管理办法》第四十七条"其他相关规定" | LLM辅助识别 + 人工标注，`to_doc` 填写目标文档名 |
| 引用外部法律 | "依照《中华人民共和国保险法》" | `to_doc` 填写法律名称，`to_article` 填写具体条号（如有），标记 `is_external_law=True` |

### 7.7.1 跨文档关系发现方法

跨文档关系的发现比同文档关系更困难，因为缺乏明确的引用文本。以下是发现跨文档关系的方法：

| 方法 | 适用场景 | 置信度 | 说明 |
|------|---------|--------|------|
| 明确引用词 | 条款中直接引用另一文档名称 | 1.0 | 如"依照《互联网保险业务监管办法》" |
| RAG语义检索 | 对每个条款用RAG检索跨文档语义相关条款 | 0.5-0.8 | 天然支持跨文档，向量检索不区分文档来源；LLM判别后确认 |
| "其他相关规定"模式 | 条款提及"其他相关规定"但未指明具体文档 | 0.5-0.7 | 需结合法规体系知识判断指向哪部文档 |
| 术语一致性 | 不同文档使用相同术语 | 0.3-0.5 | 如"保险销售人员"在多部法规中出现 |
| 主题重叠 | 不同文档对同一主题有规定 | 0.3-0.5 | 如"互联网保险销售"在两部法规中均有规定 |
| LLM语义分析 | LLM判断两条款存在语义关联 | 0.5-0.8 | 需人工验证 |

**发现流程**：

```
Step 1: 正则提取 → 发现明确引用词（如"依照《XX办法》"）
Step 2: RAG语义检索 → 对每个条款检索跨文档相关条款（推荐，见4.2.3节）
Step 3: "其他相关规定"模式匹配 → 标记为待确认的跨文档关系
Step 4: LLM判别 → 对RAG检索结果进行关系判别，确认关系类型和置信度
Step 5: 人工验证 → 确认LLM发现的跨文档关系
```

**RAG搜索发现跨文档关系的优势**：RAG检索天然不区分文档来源，一次查询可以同时召回同一文档和不同文档的相关条款。这是发现跨文档关系最高效的方法，因为不需要预先知道哪些文档之间可能存在关系。

**关键原则**：跨文档关系必须标注发现方法（source字段）和置信度，低置信度关系（<0.7）必须经人工验证后才能用于审核扩展。

### 7.8 极端情况汇总表

| 极端情况 | 检测方法 | 处理策略 | 是否阻断 |
|---------|---------|---------|---------|
| 自引用 | `from == to` | 标记，不扩展 | 否 |
| 循环引用 | DFS环检测 | `visited` 防循环 | 否 |
| 超长链 | 深度计数 | `max_depth` 截断 | 否 |
| 目标不存在 | 查找失败 | 标记 `missing`，不扩展 | 否 |
| 矛盾关系 | 同对多关系 | 全部保留 | 否 |
| 多关系并存 | 同对多类型 | 全部保留 | 否 |
| 跨文档引用 | `from_doc ≠ to_doc` | 正常处理 | 否 |
| 外部法律引用 | 文档名含"中华人民共和国" | 标记 `is_external` | 否 |

| 超长链 | A→B→C→D→E | 在 `max_depth` 处截断 |
| 目标不存在 | A引用不存在的条款X | 标记 `missing`，不扩展 |
| 空关系 | 条款无任何关联 | 正常审核，不扩展 |
| 跨文档引用 | A引用另一文档的B | 正确扩展跨文档条款 |
| 多关系并存 | A和B有2种关系 | 两种关系都展示 |

### 9.5 性能指标

| 指标 | Demo要求 | 生产要求 |
|------|---------|---------|
| 关联扩展耗时 | ≤ 50ms | ≤ 20ms |
| 传递闭包计算耗时 | ≤ 100ms（启动时） | ≤ 50ms |
| 关联扩展增加的Token消耗 | ≤ 500 tokens/次 | ≤ 300 tokens/次 |

## 附录B: 数据库Schema变更影响分析

### B.1 新增表对现有系统的影响

| 影响项 | 说明 | 风险 |
|--------|------|------|
| `_schema_version` | 从7升级到8 | 低，增量迁移 |
| `Database._run_migrations` | 新增v8迁移逻辑 | 低 |
| `Database` 单例 | 无影响，新表独立 | 无 |
| 现有查询性能 | 新增索引不影响现有查询 | 无 |
| 磁盘空间 | 预计<100条关系记录，<10KB | 可忽略 |

### B.2 审核流程变更影响

| 影响项 | 说明 | 风险 |
|--------|------|------|
| `WorkflowEngine` | 新增1个步骤 | 低，步骤独立 |
| `_step_rag_retrieve` | 无修改 | 无 |
| `_step_rerank` | 无修改 | 无 |
| `_step_expand_relations` | 新增步骤，对重排序后的Top-K条款扩展关联 | 低，步骤独立 |
| `_step_llm_reason` | 输入从重排序结果变为重排序+关联结果 | 中，需测试Token消耗和推理质量 |
| `_step_validate` | 需验证关联条款的引用合法性 | 低，复用现有验证逻辑 |

### B.3 回滚方案

如果关联扩展功能导致问题，可快速回滚：

1. 从 `WorkflowEngine` 中移除 `expand_relations` 步骤
2. 设置配置项 `ENABLE_CLAUSE_RELATION_EXPANSION=False`
3. 关联条款数据保留在数据库中，不影响其他功能
